# 実際のゲーム設定ローダーを使った比較

## 追加：ゲーム側の重複処理を削減した結果

RE:DOX 1.0.3本体を変更せず、次のゲーム側処理を改善した。

- 音声設定の20項目で文書キャッシュを共有し、同じJSONの解析を20回から1回へ削減。
- 同じ絶対パスを連続で使うときは、パス正規化と文書検索を繰り返さない。
  相対パスは毎回解決し、作業ディレクトリ変更への追従を維持する。
- C#側では通常のルートキー取得に不要だったUTF-8→文字列変換を省略する。

共有の読み込み処理の改善はnlohmann側にも適用した。RE:DOXだけにキャッシュを
追加した比較ではない。入力JSONと設定値は変更していない。

| RE:DOXの設定読み込み一式 | 変更前 | 変更後 | 観測した短縮率 |
| --- | ---: | ---: | ---: |
| 新規プロセスの初回 | 21.404ms | 17.303ms | 約19% |
| 初期化後の反復 | 8.104ms | 5.204ms | 約36% |

同じ改善後のnlohmann側は初回6.125ms・反復5.405ms。
RE:DOXは反復で約0.20ms短いが、初回は依然nlohmann側が速い。
これはゲームの読み込み経路の改善であり、RE:DOX本体のパーサー高速化ではない。
旧測定と別実行のため短縮率は今回の観測値であり、環境差を完全には除外しない。

各5プロセス、反復各35標本。改善後の反復min〜maxはRE:DOXが5.058〜5.521ms、
nlohmannが5.359〜5.568ms。初回の全観測値（ms）:

- RE:DOX: 18.462 / 17.167 / 17.264 / 17.303 / 17.642
- nlohmann/json: 6.532 / 6.125 / 6.140 / 6.040 / 6.071

文書生成は58→39回、全API呼び出しは1,522→1,484回。
取得値のトレース（文書作成・解放を除く）は旧測定と全て一致。
改善後も2方式の全トレースは5組全て一致した。
RE:DOXラッパーの既存テスト、文書の同一性・パス別名・キャッシュの寿命・
相対パスの作業ディレクトリ追従・move後の再利用・音声設定の既定値とエラーの
追加検証が通過し、本番の音声実装もRelease相当でコンパイルした。

[改善後の全標本・初回記録・検証ハッシュ](SceneSettingsOptimizedResults/)。再現:

```powershell
./Tools/SceneSettingsBenchmark/Run.ps1 -OutputDirectory x64/SceneSettingsOptimized -ProcessRuns 5
```

## 結論

今回の実装・入力では、**新規プロセスでの初回設定読み込みはnlohmann/json側が速い**。
DLL初期化後の繰り返し読み込みはRE:DOX側が約0.41ms速いが、これだけで
RE:DOXがゲーム全体で高速とはいえない。以前の「AI設定30項目の初回一括取得」の
結果だけからゲーム全体の採用を推奨するのは不十分だった。

| 測定対象 | RE:DOX | nlohmann/json | 標本 |
| --- | ---: | ---: | --- |
| 新規プロセスの初回設定読み込み | 21.404ms | **9.937ms** | 各5プロセスの中央値 |
| 初期化後の設定一式の繰り返し読み込み | **8.104ms** | 8.512ms | 各5プロセス×7標本の中央値 |

初回はnlohmann側が約54%短い。反復はRE:DOX側が約4.8%短い。
反復標本のmin〜maxはRE:DOXが7.693〜10.043ms、nlohmannが8.062〜10.720msで、
ばらつきが重なる小さな差である。統計的有意差や全環境での順位は主張しない。

初回の全観測値（ms、実行番号順）:

- RE:DOX: 40.509 / 20.746 / 21.711 / 21.309 / 21.404
- nlohmann/json: 10.027 / 9.821 / 10.021 / 9.937 / 9.693

## 比較対象

本番の`FlightSceneLoader::Load`をそのままコンパイルし、同じAssetsを使った。
自機・敵機、敵AI、カメラ、HUD、ミッション、海・空・雲、艦船、武器、
オープニングと各シネマティックを含む。加えて`CombatAudio::Initialize`と同じ
`AudioSettings::Load(JsonAssetReader{}, audio.json)`を実行した。音声デコードはしない。

RE:DOX側は本番のC#ソースをRelease Native AOTとして発行したDLLを使う。
nlohmann側はベンチマーク専用のC++アダプターで同じ呼び出し契約を実装する。
個別検索、JSON Pointer、数値の有限性・配列長検証、文字列取得、一括取得の
一度の走査と設定配置、文書単位の数値キャッシュを備える。
RE:DOX本体・ゲームのソース・パーサーの採用は変更していない。

これは**この二つの利用実装の比較**であり、nlohmannへ直接書き換えたゲームの
最適性能やパーサー内部だけの順位ではない。RE:DOX側には通常のハンドル管理・
ロック・Native AOT境界があり、nlohmann側にそれらを人工的に追加していない。
nlohmann側にもAPI振り分け等の比較用アダプターがある。
不正入力全般・重複キー・並行利用で本番互換の代替品としては検証していない。

## 初回と反復の意味

初回: 新規プロセスで、シーン設定と音声設定の読み込み開始から、取得結果と
ローダーのキャッシュの破棄まで。RE:DOX側のDLLロード・初期化、nlohmann側の
設定配置情報の初期化を含める。プロセス起動そのものは含めない。
Windowsのファイルキャッシュは消去せず、ディスクが完全に冷えた条件ではない。
初回差には初期化等が含まれるが、今回の計測だけで各要因の寄与は分離できない。

反復: 出力確認1回とウォームアップ5回の後、約150msずつ7標本。
毎回シーンを最初から読み、文書・数値キャッシュも作成・破棄する。
取得済み配列をコピーするだけの測定ではない。
ファイルI/O、存在確認、パス解決、個別検索、一括取得、設定検証を含む。
音声設定は本番同様キャッシュなしの読み方を維持した。

## 正しさの確認

計測外の実行で、JSON入力と読み出した全数値のビット列、文字列、配列長、
未指定項目の結果、一括取得の結果を順に記録し、2方式のSHA-256が一致することを
各プロセス組で確認した。5組全て一致した。

1回あたりの文書生成58回・API呼び出し1,522回（解放を含む）:

| 呼び出し | 回数 |
| --- | ---: |
| 文書作成 / 解放 | 各58 |
| 数値・数値配列の個別取得 | 954 |
| 文字列取得 | 338 |
| 配列長 | 108 |
| 型付き一括取得 | 6 |

58回はファイルの種類数ではない。同じ音声設定を何度も解析する既存経路も含む。
トレースは実際にゲームへ渡るAPI結果を比較するもので、構造体のパディングや
未参照のアセットデータまでを比較するものではない。

## 環境・再現・データ

Ryzen 5 5600X、Windows x64、MSVC C++20 Release /O2、.NET SDK 10.0.403、
Native AOT 10.0.14、CAPCOM.REDox 1.0.3、nlohmann/json 3.12.0。
計測は並行させず、プロセス組ごとに先に実行する方式を交互に入れ替えた。

```powershell
./Tools/SceneSettingsBenchmark/Run.ps1 -ProcessRuns 5
```

ツールの[詳細](../../Tools/SceneSettingsBenchmark/README.md)。
[集計・全標本・初回の記録・入力ハッシュ](SceneSettingsResults/)。
大きな検証トレース本体は`x64/SceneSettingsBenchmark/*-trace.txt`へ出力する。

GPU初期化、モデル・テクスチャ読み込み、音声デコード、最初のフレームまでの
総起動時間、FPSは対象外。**設定読み込み全体の結果を、そのままゲーム全体の
起動時間やプレイ中の性能改善として扱わない。**
